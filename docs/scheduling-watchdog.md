# External scheduling watchdog

A five-minute Cloudflare cron provides the external trigger for minute-50 hourly acquisition. The native Actions schedule remains enabled and can consume an unclaimed current slot, but the external dispatch will usually arrive first. Native recovery must be evaluated separately; an enabled watchdog can cause native acquisitions to skip consumed slots. GitHub Actions remains the collector and publisher. The watchdog has no NOAA access path. Its GitHub token has no direct Contents write permission, but Actions write can invoke other repository workflows with their existing publishing privileges, cancel runs and delete logs. GitHub does not offer a collect.yml-only dispatch token; protect this credential as a delegated publishing capability. Deployment starts disabled; the reviewed main revision and activation are explicit deployment variables.

## Slot and provenance contract

A slot is a UTC minute-50 boundary and its following hour. The Worker selects the current window from its actual invocation clock, never an older missed window. It reads a pinned data-branch snapshot, checks the live collection variable, checks the exact reviewed main revision and checks queued, running, waiting, requested and pending collection/reconciliation workflows. An active writer delays external dispatch. This check is advisory: a native run can arrive afterward, so the writer owns the final admission decision.

One SQLite-backed Durable Object, named `noaa-hourly-v1`, reserves a UUID and reservation clock before POSTing `workflow_dispatch` for `collect.yml` on `main`. Any dispatch outcome consumes external dispatch permission for that slot. HTTP 204 means accepted; timeout, connection loss and 5xx mean ambiguous. A definitive 4xx is retained as rejected. None causes automatic redispatch. A crash after reservation but before POST can leave a missed slot; preserving the ambiguity is preferable to inventing a successful acquisition. Preserve the object and its namespace across deployments and rollbacks. Do not delete reservations to retry an acquisition.

Under `evidence-writer` concurrency, collection clones fresh data, reads the original Actions run metadata and rechecks the live pause variable using a separate read-only credential. It rejects malformed external intent and a changed code commit. It skips a consumed slot, an Actions run with any existing start, or an intended slot whose window has expired. Native/manual intent uses Actions `created_at`; GitHub does not disclose the native intended delivery time, so `scheduledAt` remains null. An external dispatch explicitly supplies its intended slot, UUID, reservation time, Cloudflare cron clock and reviewed commit. A delayed cron clock may precede the current slot selected from actual invocation time; that original clock is preserved independently. A late native trigger may acquire the current window if it is still unclaimed; it cannot fill a prior window.

`data:scheduling/slots/<UTC>.json` and `data:runs/<batch>-start.json` contain identical durable start records and are committed together before requesting NOAA. The existing writer serialization prevents concurrent claims. An older start without a slot claim still occupies its actual start window. Original request/receipt clocks, raw bodies, partial responses, manifests, hashes and disagreement diagnostics remain unchanged. Additional scheduling context belongs to the hosted envelope and Release `context.json`; it does not modify original collector records. A failed, partial or interrupted attempt consumes the slot. Reconcile or recover its existing bytes; no automatic refetch repairs it.

## Observation and failure recovery

Read `/status` and Cloudflare observability logs. One pending slot is verified per tick; the current slot is prioritized at least every ten minutes so old unresolved rows cannot indefinitely delay its verification. Other pending slots within the latest 72 records are checked by oldest observation clock. Older unresolved records stay in SQLite but are not automatically rechecked; verify them with the pipeline’s recovery tools. The status endpoint lists the latest 72 slot records; older slot state remains in SQLite. Save snapshots outside the Worker for the acceptance record. From the first full window after monitoring starts (`coverageFrom`), the most recent closed window is checked for a durable claim after a 15-minute publication allowance. An absent claim becomes an actionable invocation failure and a durable `claimGaps` record naming the data snapshot; a later claim records resolution without deleting the first detection. This also catches accepted dispatches that fail before admission and windows deferred by writers. Paused collection suppresses that check until re-enabled; the separate 90-minute observed-pause signal remains active. This deadline signal is not an exhaustive historical coverage audit and does not change the existing freshness or science thresholds. `lastTick` must advance within the five-minute cadence plus disclosed delivery latency. Missing Cloudflare ticks and missing Actions starts are separate gaps. The watchdog adds a trigger failure domain; it does not guarantee Cloudflare or GitHub availability. Existing hourly/monthly audits retain original start-window, freshness and archive diagnostics and may themselves be delayed by GitHub.

`awaiting_start`, `awaiting_terminal`, `awaiting_actions_completion`, `awaiting_catalog`, `publication_failed` and `verification_failed` are not success. `completed_without_claim` discloses a skipped or failed Actions run, including expired intent. It remains observable: a pinned snapshot may precede a completed run’s publication, or another native run may later claim the window. `published_acquisition_failed` means publication verification passed but acquisition did not; retain the original failure. `published` requires a completed successful Actions run, complete terminal, matching catalog/context, an immutable Release, public archive/context equality, and every stored bundle's SHA-256 and byte length. An empty interrupted archive is a published acquisition failure, never a successful slot. A cleared verification error remains in `lastError`; the active `error` field clears on a successful recheck. The watchdog does not unpack bundles; independent acceptance must verify the full original-file inventory and Git JSON. Recovery may publish saved bytes in a separate catalog/terminal recovery record; inspect those with the pipeline's existing recovery tools rather than treating an unresolved watchdog state as acquisition success.

On an ambiguous dispatch, preserve the reservation, inspect matching Actions run titles (`NOAA receipts watchdog:<UUID>`), durable starts and Git history, and inspect reconciliation evidence. The watchdog does not follow separate recovery records; its original-attempt status may remain unresolved after a recovery, so verify recovery through the existing pipeline rather than waiting for that status to become green. On missing or failed publication, use existing `reconcile.yml` or failure-artifact recovery. Never rerun a consumed slot merely to make it green. Later slots remain eligible for new attempts. No historical receipt is reconstructed and no dispatch acceptance is counted as a successful slot.

Rolling collection back to code without the guard requires disabling the Worker first and draining its dispatched runs. An old collector cannot enforce the slot contract: pause collection, drain all writers, and keep collection paused until guarded code is restored, or explicitly review the duplicate-acquisition risk before resuming old code. Keep claims and SQLite state intact. After rolling forward, existing starts still suppress duplicate acquisition, including starts from the older code. Do not roll an old unguarded collector into an active external scheduler.
